# フィードバックを残す

使っている人の困りごとや改善の希望を、管理者が後でまとめて直せるように、1件1ファイルで `feedback/` に残す。人向けの説明は [docs/feedback-flow.md](../../../docs/feedback-flow.md)。

## いつ使うか

- 人が「フィードバック: 〜」「ここが分かりにくい」「〜できるようにしてほしい」と言ったとき。
- 作業中に、スキルや手順の問題で進められなかったとき（例: 手順どおりに動かない、マニュアルと実際が違う、同じ質問を何度もした）。このときは「フィードバックとして残しましょうか」と一言聞いてから残す。

ツールではなく案件の中身（LP の文言の直しなど）は、フィードバックではなく通常の作業として扱う。

## 残し方

1. 次を確かめる（分からなければ空欄でよい。人に何度も聞かない）。
   - 使っている版: 作業フォルダの `VERSION` の中身
   - 書いた人: 人が名乗っていれば書く（聞かなくてよい）
   - 案件番号と工程: 会話と `projects/` から分かる範囲で
2. `feedback/{YYYYMMDD}-{HHMM}-{短い題名}.md` を作る（`feedback/` がなければ作る）。題名は内容が分かる日本語で短く。
3. 書いたら、ファイルの場所と内容の要点を1〜2行で伝える。そのあとは元の作業に戻る。

## ファイルの書き方

```markdown
# {短い題名}

| 項目 | 内容 |
|---|---|
| 日時 | 2026-11-25 14:30 |
| 書いた人 | （分かれば） |
| 版 | 202611261030 (661060c) |
| 案件・工程 | 99902 牛乳石鹸 AKA・工程2 ワイヤーフレーム |
| 種類 | 困って止まった / 不便・分かりにくい / 改善の提案 / 不具合 |

## 起きたこと

（人の言葉をなるべくそのまま。何をしようとして、何が起きたか）

## してほしいこと

（人の希望。なければ空欄）

## Claude の補足

（会話から分かる状況の要約、出たエラーの文、関係しそうなスキル・ファイル。推測は推測と書く）
```

## 書かないこと

- パスワード、個人の連絡先などの個人情報。
- 案件の中身を長く写すこと（必要なら「どのファイルのどこ」とだけ書く）。
